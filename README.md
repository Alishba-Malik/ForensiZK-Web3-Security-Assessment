# ZK Application Security Assessment — ForensiZK

## Assessment Overview

This repository contains the complete findings of a **black-box and white-box penetration test** conducted against ForensiZK. The assessment covered four attack surfaces:

- **L1 — ZK Circuit Layer** (constraint system, witness construction, public inputs)
- **L2 — ZK System Misuse** (proof lifecycle, replay, context binding)
- **L3 — Backend API** (authentication, file handling, IDOR)
- **L4 — Infrastructure** (configuration, secret management, CORS)

In addition to manual exploitation, the circuit logic was formally verified by translating the Plonky2 circuit into a Solidity equivalent and running **property-based fuzz tests (Foundry)** and **exhaustive symbolic proofs (Halmos with Z3 SMT solver)**.

## What is ForensiZK?

ForensiZK is a zero-knowledge proof system designed for digital forensics. It uses the **Plonky2 proving framework** (Goldilocks field, PoseidonGoldilocksConfig) to generate cryptographic proofs of whether a Linux system log indicates a security compromise — without revealing the raw log contents.

The system is a three-tier application:

| Component | Technology | Role |
|-----------|-----------|------|
| Frontend | Next.js / React | Upload logs, display verdicts |
| Backend API | Node.js, Express, BullMQ | Job queue, file management, API routing |
| Prover Binary | Rust, Plonky2, structopt | ZK circuit construction, proof generation |
| Storage | Redis, local filesystem | Job state, proof/log file persistence |
| ZK Framework | Plonky2 (Goldilocks field) | STARK-based recursive ZK proof system |

### Key Finding

> The ZK proof generated by the circuit is **effectively decorative**. The backend reads a plaintext `VERDICT:` string from stdout to determine the forensic verdict rather than verifying the circuit's public inputs. This directly contradicts the system's core security model.


## Attack Chain — Full ZK Bypass

Three critical vulnerabilities chain into a complete end-to-end bypass:

```
Step 1 [F-05] → Download any proof file with zero authentication
Step 2 [F-01] → Submit a completely fake file — accepted as valid ZK proof
Step 3 [F-02] → Replay the same clean proof unlimited times across cases
Step 4 [F-03] → Backend reads VERDICT: stdout, never reads proof.public_inputs
                  Result: forged clean verdict for any compromised system
```



## Formal Circuit Verification (Foundry + Halmos)

Although the 3 critical vulnerabilities exist at the **application integration layer**, the circuit logic itself was independently verified to be **mathematically correct**.

### Why Solidity?

Plonky2 does not expose a direct property-testing interface. The circuit was translated from `prover/src/circuit.rs` into `circuit/ForensiZKCircuit.sol`, mirroring the exact boolean constraint system. This is standard methodology for formally verifying ZK circuit correctness.

### Two-Tier Evidence

| Tool | Method | Strength |
|------|--------|----------|
| `forge test` | Property-based fuzz testing — 10,000 random inputs per property | Probabilistic — finds bugs across wide input range |
| `halmos` | Symbolic execution — Z3 SMT solver searches ALL possible inputs | **Exhaustive formal proof** — holds for every mathematically possible input |

### Properties Verified

| # | Property | Test Function | Tool | Result |
|---|----------|--------------|------|--------|
| P1 | No false negatives — any flag → compromised | `check_NoFalseNegatives` | Halmos | ✅ PROVED |
| P2 | No false positives — no flags → clean | `check_NoFalsePositives` | Halmos | ✅ PROVED |
| P3 | SSH threshold fires at exactly 5, not 4 | `test_SSHThresholdBoundary` | Foundry | ✅ PASS |
| P4 | Bit decomposition always consistent (split_le) | `check_BitDecompositionConsistency` | Halmos | ✅ PROVED |
| P5 | Each forensic flag independently triggers verdict | `test_EachFlagAloneTriggers` | Foundry | ✅ PASS |
| P6 | Clean system with ssh_failed < 5 never compromised | `check_CleanSystemAlwaysClean` | Halmos | ✅ PROVED |
| P7 | uint8 type prevents 256→0 overflow (F-04 fix) | `test_SSHOverflowSafety` | Foundry | ✅ PASS |
| P8 | Bidirectional: compromised IFF any flag active | `check_CompromisedIfAndOnlyIfAnyFlag` | Halmos | ✅ PROVED |

**Halmos proved P1, P2, P4, P6, P8 exhaustively for all 2³⁸ possible input combinations. No counterexample was found.**

> **Critical conclusion:** Formal verification confirms the circuit logic is NOT the source of the critical vulnerabilities. The ZK math is correct. The failures exist entirely in the application layer that uses it.

## Running the Formal Verification Tests

### Prerequisites

```bash
# Install Foundry
curl -L https://foundry.paradigm.xyz | bash && foundryup

# Install Halmos (in a virtual environment)
python3 -m venv venv
source venv/bin/activate
pip install halmos
```

### Setup

```bash
# Create project and install forge-std
mkdir forensizk-verify && cd forensizk-verify
forge init --no-git
forge install foundry-rs/forge-std --no-git

# Copy circuit files into place
cp path/to/circuit/ForensiZKCircuit.sol src/
cp path/to/circuit/ForensiZKCircuit.t.sol test/
cp path/to/circuit/ForensiZKScenarios.t.sol test/
```

Add to `foundry.toml`:
```toml
[profile.default]
src = "src"
out = "out"
libs = ["lib"]
solc = "0.8.20"
build_info = true
extra_output = ["storageLayout", "evm.methodIdentifiers"]

[fuzz]
runs = 10000
seed = "0xdeadbeef"
```

### Run Foundry Fuzz Tests

```bash
# Run all tests
forge test -v

# Run with 10,000 fuzz iterations
forge test --fuzz-runs 10000 -v

# Run a specific test
forge test --match-test test_SSHThresholdBoundary -vvv

# Gas report
forge test --gas-report
```

### Run Halmos Symbolic Proofs

```bash
source venv/bin/activate
forge build

# Run all symbolic proofs
halmos --contract ForensiZKCircuitTest \
       --solver-timeout-branching 120 \
       --solver-timeout-assertion 120

# Run a specific property
halmos --contract ForensiZKCircuitTest \
       --function check_NoFalseNegatives \
       --solver-timeout-branching 120 \
       --solver-timeout-assertion 120
```

## Findings Summary

### F-01 — Verify Command is a Non-Functional Stub 🔴
**File:** `prover/src/main.rs` | **CVSS: 9.8**

The entire Verify implementation is `println!("VERIFY stub: {}", proof.display()); Ok(())`. Any file — text, image, random bytes — passes as a valid ZK proof. The backend returns `{ "ok": true }` for everything.


### F-02 — No Proof Replay Protection 🔴
**File:** `backend/routes/verify.js` | **CVSS: 9.1**

No nullifier, no consumption registry, no usage tracking. The same proof `.bin` can be submitted and accepted unlimited times. One clean proof covers any number of forensic cases.

### F-03 — Forensic Verdict Computed Off-Circuit 🔴
**File:** `prover/src/circuit.rs` + `backend/services/jobQueue.js` | **CVSS: 9.1**

The circuit correctly proves `compromised` as a ZK public input. The backend ignores it entirely and reads a plaintext `VERDICT:` string from stdout instead. The ZK proof is generated and immediately discarded.


### F-04 — No Log-to-Proof Binding 🟠
**File:** `prover/src/main.rs` + `prover/src/circuit.rs` | **CVSS: 8.2**

The Merkle tree commitment module exists in `commit.rs` but `build_merkle_root()` is never called in `main.rs` and the root is never registered as a circuit public input. Any proof verifies against any log file.

### F-05 — IDOR on Proof and Log Files 🟠
**File:** `backend/server.js` | **CVSS: 7.3**

`/uploads` and `/proofs` are served as unauthenticated static directories. All 7 existing proof UUIDs returned HTTP 200 with no authentication. Raw forensic log files containing sensitive system data are publicly downloadable.


### F-06 — No File Type or Size Validation 🟠
**File:** `backend/routes/prove.js` + `backend/routes/verify.js` | **CVSS: 6.5**

`multer({ storage })` with no `fileFilter` and no `limits`. Shell scripts, Python files, and 100 MB payloads are all accepted. A shell script uploaded as proof returns `{ "ok": true }`.


### F-07 — All Forensic Flags Exposed as Public Inputs 🟡
**File:** `prover/src/circuit.rs` | **CVSS: 5.3**

All 6 forensic indicators (`shadow`, `tmp_exec`, `outbound`, `kernel`, `net_flap`, `ssh_brute`) are registered as public inputs. Any proof recipient can read the full attack breakdown — defeating the ZK privacy property at the indicator level.

## Methodology

Testing followed a combined white-box (full source access) and manual exploit development approach:

1. **Reconnaissance** — mapping data flows, entry points, trust boundaries, ZK component interactions
2. **ZK Circuit Analysis** — constraint system review: under-constrained signals, missing range checks, public input selection, off-circuit logic
3. **ZK System Analysis** — proof lifecycle testing: replay, context binding, nullifier logic, verifier key integrity
4. **API Security Testing** — all endpoints: authentication, authorization, input validation, file handling
5. **Infrastructure Review** — configuration, secret management, deployment posture
6. **Formal Verification** — Solidity translation of `circuit.rs`, Foundry fuzz (10,000 runs), Halmos symbolic (Z3 SMT, exhaustive)


## Disclaimer

This assessment was conducted for educational purposes as part of a BS Cybersecurity pentesting course at Air University, Islamabad. All findings are based on static analysis and manual exploit development against the ForensiZK source code. No external systems were tested. All proof-of-concept attacks were performed against a local development instance only.
